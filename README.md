# Link Lyric

把任意播放器的歌词、歌单与播放状态同步到 Minecraft 的客户端模组。

不绑定单一播放器。Salt Player、Windows SMTC、MPD、本地歌词文件都只是**数据源**的一种实现；歌词可由播放器提供，也可由 LRCLIB 等**歌词源**外部补齐。不传输音频，Mod 不发声。

## 为什么这样分层

支持多个播放器（为 Spotify、网易云、foobar 各写适配器）是陷阱：适配器全要自己维护，每个都得逆向，永远追不完。

正确的通用化在协议层：模组只认一个开放的本机协议，谁想接入谁写适配器。你维护协议与渲染端，社区维护适配器。

更关键的是把**元数据源**与**歌词源**拆开：

```
播放器 ──► 元数据源 ──┐
                      ├──► 快照 + 时间轴 ──► 渲染层
歌词库 ──► 歌词源 ────┘
```

播放器不必自带歌词。这条拆分让「Spotify 不提供逐字歌词」不再等于「模组做不到逐字歌词」。

## 仓库结构

两个维度正交：**分支管 Minecraft 版本，模块管加载器**。

```
Link Lyric/
├── common/     纯 Java 内核，零 Minecraft / 加载器依赖
├── fabric/     Fabric 接线层
└── neoforge/   NeoForge 接线层
```

`common` 的硬性规则：**不得出现任何 Minecraft 或加载器 API 的 import**。它是「加第二个加载器只要几百行」和「两份平行代码库」的分界。

这条规则的代价是：真正依赖 Mojang 类型的渲染层代码（`RenderType`、
`GlyphProvider`、`VertexFormat` 这些）没法收进 `common`，只能在两个
加载器模块里各放一份。这 8 个文件（约 2100 行）是**结构性重复**，
合并会让 `common` 失去零依赖性质、连带 500 余个单测全部需要启动游戏运行时。

重复本身不危险，危险的是**静默分叉**——改了 fabric 忘了改 neoforge，
两个平台行为开始不同而编译器一声不响。因此 `:common:verifyMirroredRender`
把「除包名与平台名外必须逐字一致」变成构建检查，挂在 `check` 上：

```
渲染层已分叉: render/sdf/SdfAtlas.java，首个差异在第 6 行
```

漂移当场失败并指出行号，不必等人肉比对两份两千行的目录。

`check` 上共挂 7 道静态守卫，每一道都对应一类「编译通过、运行却不报错」的失效：

| 任务 | 抓什么 |
| --- | --- |
| `verifyMirroredRender` | 两端渲染层副本与三个界面静默分叉 |
| `verifyLangKeys` | `LangKeys` 常量与四份 lang json 键不一致（界面露出原始键名） |
| `verifyPainterParity` | 两端 `GuiPainter` 少实现一个重载（特效凭空消失） |
| `verifyNoDroppedParams` | 签名对但形参整段丢弃（形同虚设） |
| `verifyConstantsReferenced` | 常量定义了却无人引用（实际值在别处硬编码） |
| `verifyPreviewGeometry` | 界面层写死预览高度（与行数脱钩） |
| `verifyShaderUniforms` | `.fsh` 用到的 uniform 未在 json 声明（该功能恒为 0） |

最后一道是补上来的：`StrokeWidth` / `StrokeColor` 曾在 GLSL 与 `SdfRenderType`
里都用上、json 里却从未声明，而 `safeGetUniform` 对缺失 uniform 返回空实现、
不抛异常，于是描边整体失效而构建依然全绿。

### 歌词位置与拖动

平时**不画底板**，歌词直接浮在画面上。三条主指令：

`/linklyric on` 打开歌词，`/linklyric off` 关闭，
`/linklyric location` 进入位置调整（`location reset` 复位）。

此外 `/linklyric config` 打开个性化配置页，全部使用 Minecraft 原版控件：

左栏调歌词文字：时间偏移、切换时长、字号、最大宽度四根滑条，
外加羽化开关、字重、对齐、阴影三个开关与一个「字体颜色…」入口。

唱到某字时交界处的过渡带用 `ColorMath.lerp` 直接插值
「已唱色 → 未唱色」，每段取中间色并以不透明 alpha 绘制。

先前是把已唱色按递减 alpha 反复叠在未唱色上。数学上那也等价于插值，
但插值对象是**背景**：字形连同阴影一起变淡，在深色背景上就表现为
一道竖向暗痕，看着像「先有一条竖线扫过」。直接对 RGB 插值后，
结果与背景无关，才是真的颜色过渡。

**布局是多行堆叠**，不是固定双行。行数可调 1-10，`LineLayout` 把
「当前行 + 后续若干行」当作一整块，块心固定在锚点上，逐行往下排。
主行基线因此不随「有没有下一句」跳一行高，同一句歌词在有、无下一句
之间不会位移。

**行切换只做上移，不做旧行淡出**：其余行整体上移一行补位，旧主行
在换行瞬间直接消失。曾经做过 0.1 秒淡出，但淡出要求把旧句整句重画一遍，
而逐字路径的观感来自逐字抬升、逐顶点染色、强调提亮三样东西，
整句绘制只有单一颜色——已唱完的主句会在原位先闪一帧「最基础的文字样式」，
与它停留时的样子判若两句。句末本已唱完，直接消失反而干净。
问题不在淡化时长，而在「重画一份低配画面来冒充同一句」。

**逐字上浮由染色进度派生，但取用时过一道贝塞尔**。字被染到多少就升起多少，
完全染完时正好升到顶点，因此两者共用同一个进度量，没有独立的时间常数。

共用进度量不等于共用曲线。这里是两个不同的问题：

染色前沿问的是「唱到哪了」，属于**事实**，必须与音频时间严格成正比。
曲线一旦非匀速，口型与画面就脱节，而且贝塞尔尾部趋平，行尾永远差一点染不满。
所以 `targetWidthAt` 走线性，只做一次 `smoothstep` 收边。

上浮问的是「起来得好不好看」，属于**观感**。0.9px 的位移如果匀速平移，
观感是机械的台阶式跳格；`CubicBezier(0.25, 0, 0.2, 1)` 的形状是
「起步蓄力、中段抬起、尾部贴顶」，正是位移该有的手感。它只重新分配
速度分布，不改变起止时刻与总量，所以不会让颜色与位移错位——
两者仍在同一时刻开始、同一时刻结束。

把这两件事混在一起、用一个「统一线性」去覆盖，是错误的简化。

染色进度本身已是时间的函数，再叠一层会让两者错位：颜色已铺满而字还没升到位，
或者字升满了颜色却还在走。先前试过两种错法——空间余弦斜坡（前沿扫过一个字
只占波宽 1/3，上浮快到看不见），以及固定 0.28 秒的独立缓动（与染色不同步，
唱得慢时字已升满而颜色仍在推进）。

上浮不做「整行唱完就全部置满」的短路。已唱宽度是累加值，
行级数据与逐字混合时可能宽度先到而行级内进度未走完，
短路的置满会盖掉字级差异，表现为「颜色没染完字已经升满」。

**整体不透明度**作用于所有行（主行、后续行、间奏），
在渲染入口统一相乘。分散到各条绘制路径很容易漏掉某一条
（尤其降级绘制和间奏），表现为调低之后还有一行是亮的。
下限取 10%，不取 0：全透明等于歌词消失，而界面上没有「看不见」
这个预期，用户会以为模组坏了。

**抬升保持浮点，不取整**。抬升量只有约 0.9px，若在绘制前取整，
曲线只剩 0 与 1 两档，动画表现为长时间不动再跳一格。逐顶点写入接浮点
坐标，位移因此连续。这与「字形在纹素之间取样会糊」并不冲突：
混的是取样插值，不连续的是坐标量化，前者可通过字重与阴影的额外余量缓解，
后者只能靠不取整消除。

**加粗交给字体管线，不自叠描边**。用像素偏移重复绘制模拟加粗会绕过度量：
既不改字形也不改字距，只会得到错位副本（重影与颗粒），档位越高越糊。
`§l` 会走 `getBoldOffset()` 与 `getAdvance(bold)`，字形与字距一起正确，
且不增加绘制次数。原版只提供常规与加粗两档，因此不再分「粗」与「特粗」。

**字重作用于副行时不重新取整**。样式符在字体度量阶段生效，是字形属性
而非像素位移，缩放后不会引入半像素偏移。副行与主行共用同一档字重。

**叠加时必须补偿 alpha**。同一颜色叠 n 层，alpha 会累积：
未唱色只有 0.38，叠 5 层后接近 0.91，看起来和已唱一样亮，
透明度表达的「没唱到」就失效了。每层压到 `1-(1-a)^(1/n)`，
n 层叠加后整体 alpha 回到原值，粗细变了而明暗不变。

**阴影只画在中心层**。字重靠同色偏移叠加模拟，加粗档是 3×3 共 9 层。
若每层都带阴影，阴影副本会按层数倍增，全叠在几乎同一区域，
字形边缘糊成一团黑边——这正是「切换阴影后主行文字成一团」的成因。
阴影只需一份就能表达层次，笔画叠加只负责粗细。

**副行左边界按缩放后宽度算**。`drawTextScaled` 以 `(x, y)` 为原点缩放，
缩放后文字实际占据 `[x, x + width*scale]`。若用未缩放宽度居中，
副行中心会比主行偏左 `(width - width*0.8)/2` 像素，行数越多越明显。
这不是纵向问题——纵向的块心一直是对的。

**未唱内容用透明度表达**，而不是换一种灰色。灰色是第二种颜色，
会与用户选定的已唱色产生色相冲突；透明度只减弱同一颜色的存在感，
唱到与没唱到始终同一色系。非主行用同一个值（`UNSUNG_ALPHA`），
于是「未生效」在全场景下是一种统一的视觉语言。

**所有样式对所有行生效**。副行与后续行共用对齐、字重、阴影、字号缩放，
只有字号按 `SUB_TEXT_FONT_SCALE` 收一档。

**间奏提示**可配三档：空白、`···`、`间奏`。空白档不出画，
但仍重置行状态，否则间奏结束后首帧会沿用上一行的高亮进度。

**字号**靠 `Pose2D` 变换栈实时缩放整块歌词（所有行），
锚点是歌词块中心，因此调字号时位置不漂。缩放必须真的作用于绘制，
只参与宽度计算而不改字形，滑条拖动时画面会毫无变化。

**字重**只有常规与加粗两档，由 `§l` / `§r` 交给字体管线，
在度量阶段同时改字形与字距，不增加绘制次数。

**对齐**把行宽换算成左边界。左右对齐以可用区间两端为锚，而不是
「中心减半宽」重算——滚动会改变可见宽度，若每帧以中心反推，边界会跟着抖。
视口、主行、副行三处都要用同一套换算，否则长句滚动起点会偏。

中文阴影问题与以上三项无关：裁剪高度若按常量 `LINE_HEIGHT` 算出固定的
16 像素，英文字形低、阴影恰好落在框内，看起来正常；中文由 fallback 字体提供，
字形更高，阴影沉到框外被裁掉，于是「英文有阴影、中文没有」。
因此裁剪高度取 `painter.lineHeight() + LIFT_HEADROOM + SHADOW_HEADROOM`，
由平台层报告真实行高。
右栏是总开关、数据源开关、位置调整入口与恢复默认。

颜色页同样是「上预览、下操作」：顶部歌词预览，左下四个按钮切换调整目标
（已唱 / 未唱 / 翻译 / 重置），右侧是圆形调色盘，
盘下是颜色编码输入框，右边标明格式 `#AARRGGBB`。

取色盘是**方形 SV 平面加独立色相条**：横轴饱和度、纵轴明度（上明下暗），
色相由色相条决定。相比圆盘有个实质优点——明度是独立的一维，
想调暗纵向拉到底即可，不必同时追着半径跑。

方盘**不建纹理**，用两层 `fillGradient` 叠加等效：
底层左白右纯色（饱和度），上层上透明下黑（明度）。
色相一变只换一个颜色参数，不必重算 128x128 整块像素——
方盘与圆盘的关键差别正在这里：SV 平面随色相变化，纹理方案每次都要重建。

几何放在 `ColorSquare`（纯计算，可单测），界面只负责画渐变与响应鼠标。
`HsvColor` 负责 HSV 与 ARGB 互转，往返不漂移。

参考过 `Cloth Config`、`owo-lib`、`Mekanism` 三个开源实现：
前者只有十六进制输入框与色块预览（`ColorDisplayWidget` 的 `onClick` 是空方法），
后两者都是方盘方案但强绑各自的 UI 框架。可借鉴的是细节而非代码。

**所有改动即时生效**，没有「应用」按钮：渲染器每帧直接读
`LyricStyleConfig`，滑条一动歌词就变。

界面顶端是**预览框**，歌词画在里面，颜色、字号、宽度、过渡的改动立刻可见。
预览走的是真实渲染路径而不是另画一份示意——另画一份必然与真实观感走样。

配置页**继承原版 `OptionsSubScreen`**（继承 `Screen`，再叠一层
`HeaderAndFooterLayout`）。滚动、标题、页脚、控件对齐、键盘导航与朗读
全部由原版接管，自己只需要写 `addOptions()` 与预览那一行。

这里曾经是 NeoForge 手搓的一套：两栏布局、自绘滚动条、`ScrollState`
滚动数学、手写的 `OptionSlider`，约 250 行。两边因此长得不一样——
同一张配置页在 Fabric 上是原版列表，在 NeoForge 上是自绘两栏，
主开关、描边颜色、行数三处的控件形态互不相同，"取消"在一端根本不回滚
（它只是再调一次 `onClose()`，与"完成"完全一样）。
现在两端用的是**同一份界面代码**，`verifyMirroredRender` 守着不许分叉。

预览占的是列表里的若干行：`OptionsList` 的行高由 `Entry.render` 写死 20 像素，
无法给单个控件更高空间，所以塞一个隐藏占位控件连续占住 N 行，
再在自己的 `render` 里按这段实际坐标画预览。占几行由
`LyricGeometry.previewHeight` 按当前行数与行距实时算出，
写死 56 的做法在行数调大后会把副行裁掉。

另两个界面（调色、位置调整）继承 `Screen` 且**由自己控制绘制顺序，
不调 `super.render`**：反编译 `Screen.render` 可以看到它一进来就先调
`renderBackground` 再遍历控件，于是「先自绘内容、最后调 `super.render`」
会让背景遮罩重画一遍压在最上层——整个界面发暗，只有按钮亮着，
因为按钮恰好在遮罩之后才画。正确顺序是：先 `renderBackground`，
再自绘内容，最后逐个画控件。

这两个界面必须覆盖 `renderBackground`。1.20.5 起所有 Screen 默认给整屏
叠一层高斯模糊，画在界面里的东西——包括预览框里的歌词——都会被糊掉。
这就是「预览区看起来和背景同一层、发虚」的真正原因，不是画序或透明度问题。
歌词预览要看清像素级细节（羽化、抬升、颜色过渡），模糊让它失去意义。
配置页继承 `OptionsSubScreen` 后仍要覆盖它，理由相同。

预览用 `setPreviewArea(Bounds)` 实现：渲染器按该矩形重新居中，
并忽略用户偏移。偏移描述的是「相对全屏底部的位置」，在预览框里没有意义，
而且几十像素就能把文字顶出框外。预览中也不滚动，超长直接截断：
滚动会让文字横向跑出框，而预览要看的是颜色与排版。退出界面时必须清除预览区，
否则下一次 HUD 绘制会把歌词画进那个框里。

时间偏移只作用在「查时间轴」这一步，不动外推时钟。若直接偏移时钟输入，
外推锚点会跟着漂移，暂停恢复后累积误差；在这里加常量相当于整体平移时间轴，
语义干净且可逆。

数据源开关与连接状态分开：禁用只让 `isAlive()` 返回 false 从而停止出画，
后台轮询继续跑，重新启用立刻有数据，不必等重连。开关状态单独持久化，
重启后保持禁用。

`/linklyric location` 会打开一个**全透明界面**，此时光标可见。
配置页里的「调整位置…」也走这里，两者是同一个界面。

语义是**先拖、后确认**：按住歌词拖动只改屏幕上的位置，松手既不落盘也不退出，
可以分多次拖、反复微调；点「保存」（或回车）才写盘并关闭，
点「取消」（或 Esc）回到进入时的位置。未保存时顶部会提示「位置已改动，尚未保存」。

这条语义要求拖动结束时**不能**顺手落盘。控制器的 `end()` 只停止跟随，
`commit()` 才写盘，`revert()` 回滚到会话起点。
若在 `end()` 里落盘，点取消也回不去，撤销就无从实现。

保存后再进入调整，回滚基线会更新到新位置——否则第二次调整点取消会跳回很早以前的位置。

为什么必须开界面：HUD 状态下光标被游戏锁在窗口中心，
玩家既看不见指针也无法按住拖动。界面本身不画背景，
只叠一层歌词与拖动底板，下方游戏画面保持可见；单人游戏也不会因此暂停。

按下点必须落在歌词包围盒内才算开始拖动。空白处按下不拖，
界面把这次操作当作放弃并关闭——避免误触把歌词甩到边上。
界面用 `mouseDragged` 给出的当前光标位置计算，而不是帧间增量 `dragX/dragY`：
掉帧时增量会丢，累计位移的方式更稳。

命中检测依赖 `FloatingLyricRenderer.bounds()`：歌词最近一帧的屏幕包围盒。
它是**渲染的副作用**而不是纯查询，因为范围取决于字体宽度与滚动偏移，
只有真正画过一次才知道。因此每帧开头统一清空、由出画路径写入，
没有出画（关闭、无歌词）时为空——空包围盒不命中任何点，
看不见的歌词不会抢鼠标。

关闭状态下执行 `location` 会**自动打开**歌词：用户正是在靠它调位置，
拖一片空白没有意义。

位置存成**相对屏幕中心的偏移**，不是绝对坐标：换分辨率、改 GUI 缩放之后，
歌词仍停在画面相同的相对位置，不会跑到屏幕外。默认值 `(0, 0)` 等价于原先的
「底部居中」。

两个实现约束值得记下来：

Fabric 的 `ScreenMouseEvents` 只有 click/release/scroll，**没有鼠标移动事件**。
拖动位置因此由 `ClientTickEvents` 按 tick 轮询光标，20Hz 足够跟手；
确认与取消仍走 Screen 事件，这样拖动期间能吞掉点击，避免误触界面按钮。

光标坐标必须用 `getGuiScale()` 换算成 GUI 坐标。直接用窗口像素会让
高 DPI 下的位移被放大数倍。

指令入口拿不到「按在歌词上」这个前提，所以首帧只用来确定基准点，不移动：
否则一执行指令歌词就瞬移到光标处。

### 逐字染色为什么不能「直接算宽度就画」

染色要连续，靠的不是算得准，而是**跨帧保持状态**。这里踩过四个坑，
每一个都会让高亮停在原地或整行瞬亮，症状几乎一样，排查时极易混淆：

**歌词指纹不能取 `seq`。** 桥接端的 `seq` 每次位置上报都会递增，
用它做歌词缓存键，时间轴会每秒被重建一次，渲染层的换行状态被反复重置，
结果是每帧都跳过平滑、直接把已唱宽度赋成目标值——表现为整字跳变。
指纹必须只对 `lyric` 对象本身做哈希。

**帧间隔要在入口统一算。** 若只在「同一行」分支里取 `nanoTime`，
换行那一帧不会记录时间戳，下一帧间隔被算成 0，平滑推进失效。

**外推必须限幅且单调。** 轮询滞后时外推会无界前冲，位置越过整行后
`indexAt` 停在末行并判定已唱完，整行恒亮——看起来像「没有染色」。
限幅之外还要保证同一次播放中位置不倒退，否则轮询抖动会让高亮闪烁；
但跨行、seek、换曲这类大跨度回退必须放行，不然会永久卡在旧行。

**上报周期是 1 秒，不是轮询间隔。** 轮询每 200ms 发一次，但宿主每秒才更新
一次位置，同一份位置会连续返回 5 次。外推余量若小于这个周期，高亮走完余量
就停住等下一条上报——现象正是「一秒一跳、中间明显停顿」。
余量必须按实测周期自适应，且上限要随本地时间一起推进；若写成
`reportedMs + lead` 这种固定上限，位置追上上限后就再无前进余地。

**行级歌词要按行内比例插值。** 宿主并非总提供逐字时间：换到一首没有逐字
数据的歌，`lyricsCells` 就只有 1 个元素。此时若按「到点全亮」处理，
高亮会整块跳变。按行内时间比例做线性推进，观感接近卡拉OK，
且不伪造原数据里并不存在的字级时间。

**字级上浮按字号比例，不取整。** 幅度是 `字号 × 0.10`，保持浮点：
取整会把 0.9 压成 1，叠上绘制端的取整，整条曲线只剩 0 与 1 两档，
表现为长时间不动再跳一格。抬升量与染色进度是同一个量，
字被染到多少就升起多少；但抬升在取进度时过一道贝塞尔给出位移手感，
染色前沿保持线性以便与音频对齐——两者起止时刻相同，只是速度分布不同。
裁剪预留空间必须由同一个幅度算出，否则抬起的字顶部会被削平。

**主次靠字号与透明度拉开，不靠换色。** 副行字号是主行的 `0.8` 倍，
宽度按缩放后计算，否则居中会偏左 `(width - width×0.8)/2` 像素。
未唱文字用同一个颜色降低 alpha（`0.38`），而不是换成灰色：
灰色是第二种颜色，会和用户选定的已唱色产生色相冲突。

**逐字高亮用两层真实颜色，不是一层加蒙版。** 整行先以未唱色铺满，
再把已唱段用已唱色重画一遍。两层共用同一个 `textX` 与同一份抬升表，
只有裁剪区不同，因此像素严格重合，得到的是真正的变色。
关键约束是两层不得各自位移：坐标一旦分叉，两种颜色就会在中途对穿，
形成重影。这条约束当前由逐顶点染色接管——一个字的左右顶点各带一色，
GPU 在字内插值出前沿，两层绘制退化成一层，坐标分叉的可能从根上消失。
「整行未唱色 + 已唱段重画」的路径仍保留，供不支持逐顶点染色的平台降级使用。

Salt Player 本身用单层加黑色蒙版，是因为 Compose 的 `Text` 必须一次画完
才能局部覆盖，拿不到「同一串字分两段上色」的能力。Minecraft 的 HUD
可以用两次绘制配裁剪区做到，代价就是上面那条坐标一致的约束。

**长行要滚动，不能截断。** 截断丢掉的是副歌后半句，而歌词恰恰是「想看下一句」
需求最强的地方。滚动规则取自 `ScrollStepper`：演唱点越过视口中线才推动文本，
推动量恰为超出中线的距离，并夹在 `[-(行宽-视口宽), 0]`。
这样演唱中的字始终停在中线附近；若改成按时间匀速滚，速度会与演唱脱节，更难跟。
滚动时所有裁剪区都必须再夹一次视口，否则已唱段会画出面板、压到别的 HUD 上。
### 字内渐变：为什么最终没用裁剪

用裁剪切条带模拟渐变这条路行不通，原因不是参数没调好，
而是**裁剪本身有量化下限**。

**整像素裁剪决定了分色台阶数。** 裁剪边界只能落在整数像素上，
而一个汉字在 9px 字号下只有 9 像素宽。因此染色前沿最多只有 9 个可停留的位置，
实测能观察到多帧裁剪区完全相同、随后整像素跳一格——
现象就是「先亮一列像素，然后后面的瞬间渲染完」。
这条限制无法靠增加条带数量或调羽化宽度绕过。

**改成逐顶点配色后限制消失。** 字形是四边形，
`VertexConsumer.setColor` 是逐顶点调用的，颜色本身是浮点量。
给左两顶点已唱色、右两顶点未唱色，GPU 逐像素插值，
前沿就能落在字内任意亚像素位置。
一个字只画一次，不再需要条带，也不需要为分色开裁剪。

实现分三层：

`GradientColorizer`（common，纯计算）决定每个字的左右端点色：
完全在前沿左边取已唱色、完全在右边取未唱色、跨越前沿则左已唱右未唱。
位置信息由顶点几何承载，颜色只需要表达「是否跨前沿」。

`GradientGlyphWriter`（平台层）按原版几何写四个顶点。
几何必须与 `BakedGlyph.render` 完全一致，包括斜体补偿
`x0 += 1 - 0.25 * up`，否则斜体字的染色区会横向错位。
UV 与位置的对应顺序也不能变，否则字形会翻转。

`GlyphColors` 作为跨层值对象，让 common 层不必知道 Minecraft 类型。

**用 `VarHandle` 而不是 Mixin。** 需要的只有 `u0 u1 v0 v1 left right up down`
八个私有字段。为读字段引入 Mixin 要在 Fabric 与 NeoForge 各配一份
`mixins.json`、各写一个 accessor、并在每次 MC 更新后复核字段名。
`VarHandle` 只依赖字段名，且字段改名时 `available()` 转为 false，
自动退回原版单色绘制——功能降级但不会崩。

**1.21.1 和 26.1.2 的 API 完全不同，不能照抄。** 1.21.1 的 `BakedGlyph`
是普通类，`render` 把颜色当标量接收，UV 是私有字段，只能自己写顶点。
26.1.2 引入了 `RenderPipeline` 与 `TextRenderable`，
后者直接把 `VertexConsumer` 和矩阵暴露出来，顶点级着色是公开能力，
不需要任何反射。因此 26.1.2 的移植方案见「待办」一节。

**阴影要自己画。** 原版是先用阴影色画一遍、再用主色在 `x - 1` 处画一遍，
阴影色是原色 RGB 乘 0.25、alpha 不变。自己写顶点时必须复刻这个顺序与偏移，
否则开关阴影时字会横向跳动。

**加粗仍走样式符。** 字重由 `§l`/`§r` 表达，不在平台层重复绘制。
逐顶点路径上一次只画一个字，包裹样式符不会让其他文本碎片化；
不这么做的话，落在前沿上的那个字会变成常规字重，与同行其余字不一致。

**换行只改不透明度，谁都不位移。** Salt 的当前行与非当前行是两个静止的行位，
切换时按同一条 700ms 曲线交叉淡化。给任一方加纵向位移，都会让两行在
中途重叠成「两层字对穿」——即使颜色已经统一，位移本身也会毁掉单层结构。

对应的回归测试在 `common/src/test/.../hud/`：
`ProgressCurveTest` 用真实桥接数据校验曲线单调与收敛，
`LiveBridgeAnimationTest` 直接连 `127.0.0.1:35400` 实跑，端点未启动时自动跳过。

### 强调动画

够长的词组被唱到时整体上浮、向两侧展开并提亮，行末那一组幅度更大，
让句子收尾有落点。参数移植自 AMLL 的 emphasize 动画：组时长至少 1 秒才参与，
CJK 不限字数，非 CJK 限 2 到 7 字；幅度按组时长推导，有上限。

缓动是**脉冲形**：0 起、中点达峰、终点归零。这一点容易看错——
它看起来像「渐入后保持」，实际是「亮一下再走」，动画结束强调完全消失。
单元测试按脉冲形写，包含中点峰值与终点归零两条锚。

**发光用提亮，不用光晕。** 原版字体是位图图集，字形按整像素对齐取样；
任何位移或缩放都会让笔画按非整数倍采样，9px 的字立刻发虚。
把同一个字向四个方向各画一次叠成光晕，在 9px 上等于四个错位的副本互相覆盖，
字会糊成一团。所以这里只改颜色：沿 RGB 向白色插值、保留 alpha，
像素一个都不动，边缘仍是图集里的抗锯齿值。

同理，强调**不做缩放**。AMLL 的 1.1 倍放大在 Compose 的矢量字体上没问题，
在这里会让整个字重新采样。这条有专门的测试守住（`强调不做缩放以免位图字体发糊`）。

中文按单字成词，因此连续汉字的强调组最多 5 字、动画最长 2.4 秒。
上游的「词」本身就限制在几个字，本项目逐字切分，必须自己设这个窗口，
否则一句慢歌会聚成一个十几秒的巨型组，整句持续发亮。

### 逐字时间的残缺与重叠

歌词源给出的字级时间经常不完整，而残缺在行中间看不出来：染色只是
「找一个包含当前时刻的字」，没人所处的字会被直接跳过。但行末没有下一个字
可以接住填充，推算会跑出数组边界、把整行报成已唱——最后一个字在一帧内跳完。

修补放在时间轴构造时一次性做完（`LyricTimingFix`），不在渲染层逐帧判断：
这是数据的性质，与绘制无关。规则是让一连串 `end == start` 的字按顺序
均分到「该段结束」为止，界由后一个开始更晚的字、或行末决定。
行末本身也不晚于该段起点时（只按字计时的文件就是这样），退用下一行的开始，
但**上限 4 秒**——歌手能把一个音拖过整副歌，没人能拖过间奏，超过就交还给间奏提示。

**重叠的两行必须都显示。** 主唱一句还没唱完、伴唱已经进来，在歌词数据里是正常现象。
只按开始时间取一行，另一句连词带译文都会消失——不是画得难看，是内容缺了。
`LyricTimeline.activeLinesAt` 用前缀最大结束时间把向前扫描限制在常数步内：
若某行之前的所有行都已唱完，再往前不可能还有活跃行。

**不做的事。** 没有引入外部解析器：`LyricWord` 目前全部来自桥接插件，
数据源单一。等接入本地 LRC 或在线歌词源时，才需要处理格式识别、
不规则小数时间戳（`.1` 是 100ms 不是 1ms）、译文就近匹配这些事。

### 两个必须知道的坑

**映射名不是 Yarn。** 1.21.1 分支用 Mojang 官方映射：`GuiGraphics`、`Minecraft`、
`DeltaTracker`。写成 `DrawContext`、`MinecraftClient`（Yarn 名）会直接编译失败。
26.1.2 分支的类名又不同，不能照抄。

**`implementation(project(":common"))` 不进制品。** 它只影响编译期，
jar 里不会有 common 的类，装进游戏立刻 `NoClassDefFoundError`。
必须在 `jar` 任务里显式 `from(project(":common").sourceSets.main.get().output)`。
另外不要同时用 `include(project(":common"))`，那会生成嵌套 jar 与展开的 class
形成重复。

### 渲染性能约定

轮询在独立线程每 200ms 一次；`pollSnapshot()` 只做一次 volatile 读，绝不发网络请求。
断连要连续失败 6 次（约 1.2 秒）才清空，避免插件重载时歌词闪烁。
不为歌词文本构造 `Component`——中文歌词每帧重建会产生大量短命对象。

## 内核结构

```
common/src/main/java/com/linklyric/core/
├── capability/   Capability, CapabilitySet     能力声明与集合运算
├── lyric/        LyricTimeline, LyricLine, LyricWord, LyricTimingFix
├── sync/         PlaybackClock, PlayerSnapshot, TrackIdentity
├── style/        LyricStyle                    多样式几何预设（尚未接入渲染）
└── protocol/     Protocol                      跨进程契约常量
```

`core` 只放**纯数据与纯计算**：不引用任何 Minecraft 或加载器类型，
因此可以在没有游戏运行时的 JVM 里直接测。编排与渲染在 `common`，
平台适配在 `fabric` / `neoforge`。

这条界线的实际用途是保证测试可跑：`common:test` 里 500 余个用例
全部不需要启动游戏。一旦有 Minecraft 类型漏进 `core`，整条测试链立刻失效。

这里曾有一整套未被使用的编排层（`LyricSession` / `ScrollModel` /
`LyricCache` / `LyricProvider` / `SourceProfiles` / `PlaybackSource`），
只被一个单元测试引用，生产路径一次都没走过；`LyricSession` 的类注释
还写着「渲染层每帧调 `tick()` 再读 `view()`」，与实际链路正好相反。
读代码的人会照着它去找一条不存在的调用链，所以整组已删除。

**能力探测是架构核心。** 不做能力声明，代码会烂在无数个 `if (source == ...)` 里。

| 数据源 | 元数据 | 进度 | 逐字 | 队列 | 按索引播放 | 成本 |
|---|---|---|---|---|---|---|
| Salt Player 插件 | ✓ | ✓ | ✓ TTML | ✗ | ✗ | 低，纯 Java |
| Windows SMTC | ✓ | ✓ 可外推 | ✗ | ✗ | ✗ | 中，需非 Java 组件 |
| MPD / foobar | ✓ | ✓ | ✗ | ✓ | ✓ | 中，纯 Java |
| 本地 LRC/TTML | — | ✗ | 部分 | ✗ | ✗ | 极低 |

Salt Player 的「队列 ✗ / 按索引播放 ✗」不是待办，而是实测定论：插件 API 的
`WorkshopApi.Playback` 只暴露 `play/pause/previous/next/seekTo` 与当前曲目，
**没有任何队列访问入口**。虚报这两项会得到一个永远为空的歌单列表。

能力声明已经贯通到快照（`SnapshotParser` 解析 → `PlayerSnapshot.capabilities()`），
但目前唯一被渲染层读取的是 `PLAYBACK_POSITION`——没有它就无法逐字推进，
只能整行显示。`QUEUE` 等其余能力尚无消费方，因为依赖它们的界面还不存在；
先声明再实现消费方，比事后往 `if (source == ...)` 里补分支便宜得多。

## 网络与代理

**JVM 不读取 Windows 系统代理设置。** 直连 `maven.neoforged.net` 时 Cloudflare 会直接断开 JVM 的 TLS 握手：

```
SSLHandshakeException: Remote host terminated the handshake
```

同一个 URL 用 PowerShell（走系统代理）请求却返回 200，极易误判成仓库地址写错。实测调整 `jdk.tls.client.protocols`、禁用 status_request 扩展均无效——这是握手指纹层面的拦截。

解决办法是在**用户级** `~/.gradle/gradle.properties` 显式配置代理，而不是写进仓库：

```properties
systemProp.http.proxyHost=127.0.0.1
systemProp.http.proxyPort=7890
systemProp.https.proxyHost=127.0.0.1
systemProp.https.proxyPort=7890
systemProp.http.nonProxyHosts=localhost|127.0.0.1
systemProp.https.nonProxyHosts=localhost|127.0.0.1
```

## 待办：26.1.2 的渲染架构

26.1.2 把文字渲染重构成了公开的管线 API，1.21.1 那套 `@Accessor` + 反射的做法
在新版本上属于绕远路。移植时不要照搬，改用下面这条路径。

**已有的公开能力。** `TextRenderable` 的签名是

```java
void render(Matrix4fc pose, VertexConsumer buffer, int packedLightCoords, boolean flat);
```

它同时提供 `textureView()`、`guiPipeline()` 与 `left/top/right/bottom()`
也就是字形的位置边界、纹理视图与管线都是公开可读的。
1.21.1 里要靠 `VarHandle` 撬开的 `u0/u1/v0/v1/left/right/up/down`，
在这一版不需要了。

**渲染管线也是公开可构造的。** `GlyphRenderTypes.createForIntensityTexture` 与
`createForColorTexture` 都是 public static，返回的 record 直接带
`RenderPipeline`。因此自建带颜色插值的管线是正常用法，不是 hack。

**顶点格式要确认。** `DefaultVertexFormat.POSITION_TEX_COLOR` 含 COLOR 分量，
这是逐顶点配色成立的前提。移植第一步应当是
`RenderPipelines.GUI_TEXT` 的实际 `withVertexFormat` 取值——
若该管线不带 COLOR，就不能沿用它，需要按上面的 record 自建一条。

**移植后的结构可以简化。** 平台层不再需要：

- 反射取字段（`GradientGlyphWriter` 的 VarHandle 部分整个删掉）
- 手算 UV 与斜体补偿（`TextRenderable` 已给出边界）
- 降级判定（字段不会因改名而失配）

保留的是 `GradientColorizer` 与 `GlyphColors`——
这两个在 common 层、纯计算、与 MC 版本无关，可以直接复用。

**验证顺序。** 先确认 `GUI_TEXT` 的顶点格式是否含 COLOR；
再写一个只画单个字形、左右端点色明显不同的最小用例；
最后接入 `FloatingLyricRenderer`。
跳过第二步会很难定位问题——颜色不对可能来自管线格式、UV 顺序或插值设置，
三者症状相似。

## 参考源码与致谢

强调动画的算法、参数与缓动曲线来自下列项目。这里只列**代码、设计或数据确实进了本仓库**的项目，
不是「有所耳闻」的名单：每条都写清取用了什么，否则无法与源码对照核验。
名称保持各作者自己的写法，不译。

### 动画

**applemusic-like-lyrics（AMLL）** — <https://github.com/amll-dev/applemusic-like-lyrics>
逐字 emphasize 动画的原始出处。取用其参数体系：
组时长门槛（≥1s）、CJK 不限字数而非 CJK 限 2..7 字、幅度按时长推导
（`amount = powerCurve(du/2000) × 0.6`，`blur = powerCurve(du/3000) × 0.5`，上限 1.2 / 0.8）、
行末组放大 1.6 / 1.5 / 1.2 倍、逐字错峰跨度 `du / 2.5 / 字符数`、
向两侧展开 `0.03em × (n/2 - i)`、上浮 `0.025em`，
以及分段三次贝塞尔缓动（前段 `cubic-bezier(0.2, 0.4, 0.58, 1)`，后段 `1 - cubic-bezier(0.3, 0, 0.58, 1)`，中点 0.5）。

**Lyricon**（Tomakino / Proify）— <https://github.com/tomakino/lyricon>
本仓库移植时的直接参照实现（Apache-2.0），AMLL 的参数体系经其转写为 Android Canvas 版本。
取用其工程细节：贝塞尔结果预计算为 512 项查找表（逐字特效每帧调用上百次，
直接求解是 CPU 热路径）、缓动**脉冲形**这一关键语义（0 起、中点达峰、终点归零，
而非「渐入后保持」）、`WaveLiftEffect` 的脉冲参数（唱到后保持 `0.05em` 浮位，
另叠提前 400ms、时长 `max(1s, 词时长) × 1.4` 的 `sin(πx)` 脉冲）、
以及动画强度按「视图可用高度 / 完整动画所需高度」收缩、下限 0.2 的做法。

**HyperMusicCover** — <https://github.com/zyl6932/HyperMusicCover>
提供通往 Lyricon 与上述致谢清单的线索。其歌词**渲染**由 Lyricon 的 `LyricView` 承担，
本仓库未从中取用代码；其 `LyricParse` 的歌词数据归一化思路（译文按时间就近匹配、
缺失时间的尾巴闭合）在对比中作为参照。

### 与上游的差异

以下几处是**刻意不照搬**的，原因见「强调动画」一节：

- 不做缩放（AMLL 的 1.1 倍）。原版字体是位图图集，非整数倍缩放会让 9px 的字重新采样而发虚。
- 发光用原位提亮，不用光晕。四向偏移在 9px 字形上等于四份错位副本互相覆盖，字会糊。
- CJK 组加 5 字、2.4 秒双上限。AMLL 的「词」天然限制在几个字，本项目按单字切分，必须自己设窗口。

## 桌面端适配器顺序（重要）

第二个适配器**不要选 SMTC**。它覆盖最广，但唯一需要引入非 Java 的 .NET sidecar；若第二个就做它，出问题时无法区分是协议设计错了还是 helper 写错了。先用纯 Java 的 MPD 或本地 LRC 把协议验证干净，再上 SMTC。
