# Link Lyric 进程间协议（草案 v2）

适配器与 Minecraft 模组运行在两个独立进程中，必须走进程间通信。本文定义最小契约。

协议**不假设任何具体播放器**。Salt Player、SMTC、MPD 的适配器都只是同一个协议的实现。

## 传输

**当前实现是 HTTP 轮询，不是 WebSocket。**

- 地址：`GET http://127.0.0.1:35400/lyric`
- 角色：**适配器起服务端，模组作为客户端**。适配器生命周期短于游戏，
  它退出后模组只是拿不到数据，不需要任何探测或重连协议。
- 模组侧在每次请求结束后等待 200ms（`BridgePlaybackSource.POLL_INTERVAL_MS`）再发起下一轮，
  并非固定每 200ms 完成一次请求。请求在独立后台线程执行，渲染帧内零网络调用。
- 仅 HTTP 200 响应进入快照解析；单次响应是一份 `snapshot` 对象（见下节），不承载消息序列。
- 连续失败 6 次才判定断连并清空显示，成功响应会重置失败计数。
  实际时间包含请求耗时与轮间 200ms 等待，不保证 1.2 秒；连接超时为 500ms，读取超时为 800ms。
- 响应体上限 4 MiB，超限按一次失败处理（`Protocol.MAX_PAYLOAD_CHARS`）。
- **不要绑定 `0.0.0.0`**。回环以外的任何地址都需要先加鉴权。
- 读取用 `readBounded` 而非 `readAllBytes`：端口任何本机进程都能监听，
  无上限读取等于把游戏堆交给对端决定。
- **连接复用（HTTP/1.1 默认）**：同一条 TCP 连接上可连续发多个请求，
  直到任一方声明 `Connection: close`。空闲超过 2 秒适配器主动收线。
  适配器曾固定回 `Connection: close`，导致模组侧整套复用逻辑完全失效——
  每秒 5 次轮询就是每秒 5 次 TCP 握手，Windows 上还会堆积 TIME_WAIT。

早先的设计是 WebSocket 推送多消息。改成轮询的原因是：一首歌的位置只需
每秒级时效，200ms 轮询在回环上的开销可以忽略，却省掉了握手、心跳、
断线重连、背压这一整套状态机——而那套状态机是这类模组最容易出 bug 的地方。

原始推送设计里的四类消息（握手、状态、指令、回执）**不在本协议内**，
本文不描述它们。适配器不得依赖任何双向通道：模组只发 `GET`，
没有回执、没有订阅、没有连接状态。若将来需要双向控制，再按当时的
实际需要重新设计，比提前把一套状态机写进文档、再让代码永远追不上要诚实。

## 设计纪律

**只同步锚点和事件，不同步推导结果。**

当前行索引、逐字进度、滚动位置全部由模组侧从「锚点 + 播放位置」算出。任何「再推一个当前行索引」的设计都会制造两份可能不一致的真相。

**歌词不必来自播放器是分层设计目标。** 快照里的 `lyric` 可整体省略，
但外部歌词源尚未实现，当前模组不会自动查询或补齐歌词。

**播放位置不能省**。`positionMs` 是驱动逐字染色与换行的时间锚点，
HTTP 响应缺失该字段会被拒绝，按一次失败处理，而不是默认成 `0`。

## 能力声明

能力随快照下发，不需要单独的握手消息。以下仅为字段片段，不是可单独返回的完整快照：

```json
{
  "capabilities": ["TRACK_METADATA", "PLAYBACK_POSITION", "TRACK_DURATION", "TRANSPORT"]
}
```

取值见 `Capability` 枚举：`TRACK_METADATA`、`PLAYBACK_POSITION`、
`TRACK_DURATION`、`INLINE_LYRIC`、`WORD_LEVEL_LYRIC`、`QUEUE`、
`PLAY_BY_INDEX`、`SEEK`、`TRANSPORT`、`ARTWORK`。

`SnapshotParser` 忽略未知能力名，但数组元素必须是字符串；类型错误仍使响应失败。
省略 `capabilities` 时使用空集合，能力声明不能代替快照必需字段。

## 载荷

### 快照

每次 `GET /lyric` 的完整响应体。换曲、换歌词、播放态变化都体现为
同一份结构的字段变化——模组不需要区分「事件」与「状态」。

```json
{
  "v": 2,
  "type": "snapshot",
  "seq": 42,
  "track": {
    "title": "曲名",
    "artist": "艺术家",
    "album": "专辑",
    "durationMs": 243000
  },
  "positionMs": 12340,
  "playing": true,
  "lyric": {
    "wordLevel": true,
    "lines": [
      {
        "text": "原文",
        "translation": "翻译",
        "startMs": 12000,
        "endMs": 15000,
        "speaker": "",
        "words": [
          { "text": "原", "startMs": 12000, "endMs": 12400 }
        ]
      }
    ]
  }
}
```

HTTP 响应必须是 JSON 对象，且包含以下字段（字段类型不做隐式转换）：

- `v`：整数 `2`；`type`：字符串 `"snapshot"`。
- `track`：对象，必需 `title`、`artist` 字符串与 `durationMs` 整数；`album` 可省略，默认空字符串。
- `positionMs`、`seq`：整数；`playing`：布尔值。
- `capabilities` 可省略，默认空集合；提供时须为字符串数组，未知能力名忽略。
- `lyric` 可整体省略；未标记 `lyricOmitted: true` 时，缺失表示空歌词，不会自动查询外部歌词源。
- 提供 `lyric` 时须为对象，`lines` 为必需数组；每行必需 `text` 字符串、`startMs` / `endMs` 整数，`translation` / `speaker` 可省略，默认空字符串。
- `words` 可省略；提供时须为数组，每项必需 `text` 字符串及 `startMs` / `endMs` 整数。无逐字数据时走行级处理。
- `lyric.wordLevel`、顶层 `lyricOmitted` 可省略；提供时须为布尔值。`lyricOmitted: true` 不得与 `lyric` 字段同时出现，缓存条件见下节。

整数通过 `Long.parseLong` 精确读取，必须使用十进制整数字面量且落在有符号 64 位范围内；
小数、指数形式（如 `1.0`、`1e3`）、字符串数字或溢出值均拒绝，不经过浮点转换或取整。
JSON 解析深度上限为 64：根值深度为 0，递归值深度达到 64 即拒绝；未知字段的值也受此限制。
重复对象键、尾随内容、非法 JSON、必需字段缺失或已知字段类型错误均使整份 HTTP 响应按一次失败处理。
未知字段可以忽略，但不豁免 JSON 语法与深度校验。

`durationMs` 是歌词匹配的一等参数，不是可选项。同一首歌的录音室版与 Live 版
标题完全相同，只有时长能区分。`TrackIdentity.cacheKey()` 因此把时长量化成桶
（容忍 1 秒误差）后一并参与键值，避免不同版本共用同一份缓存。

### 歌词内容未变时省略（条件请求）

歌词体积远大于播放状态字段，内容未变时可通过条件请求省略：

1. 适配器在响应头回 `ETag`，值是**歌词子树**的指纹（不是整份响应的）。
2. 模组下一轮带 `If-None-Match: "<指纹>"`。
3. 指纹未变时，适配器在正文里不发 `lyric` 字段，改为 `"lyricOmitted": true`；
   `positionMs`、`seq`、`track` 等照常下发，一个字节不少。

整份响应不能作为 ETag 的载体：`positionMs` 每轮都变，指纹永不命中。
实测 40 行带逐字时间的歌词 25336 字节，省略后 342 字节（1.3%）。

**接收方必须显式读 `lyricOmitted`，不能用歌词指纹推断。**
歌词被省略时子树不存在，指纹会退化为 `0`；若拿 `0` 与上轮指纹比较，
会被判成「歌词变了」并解析出空时间轴，正在显示的歌词当场消失。

省略响应仍须为 HTTP 200 并通过完整的 v2 快照校验，不使用 HTTP 304。
模组仅在本轮请求已有可用 ETag，且响应 ETag 缺失或与请求所用 ETag 一致时接受
`lyricOmitted: true`；无已知 ETag 或响应 ETag 不一致均按一次失败处理。
接受省略响应只更新快照与能力，保留原歌词时间轴、本地指纹及 ETag；
省略标记与 `lyric` 同时出现则拒绝，即使 `lyric` 为 `null`。

非省略响应成功后，以响应 ETag 替换缓存（未返回该头则清除 ETag）。
ETag 会去除首尾空白、`W/` 前缀和外层引号，空值视为无 ETag；
仅缓存非空 ETag 时才发送带引号的 `If-None-Match`。
连续失败达到 6 次判定断连，以及调用 `stop()` 时，都会清空快照、歌词、能力、
本地指纹与 ETag；此后不能凭旧 ETag 接受省略响应，需要先成功取得非省略快照。
不足阈值的失败保留缓存，成功响应重置失败计数。

不支持条件请求的适配器可以一直返回非省略响应，但仍须满足 HTTP 的严格 v2 契约。
不支持 ETag 不能与兼容旧版本信封混为一谈。

另有一层本地指纹：解析器对响应体里 `"lyric"` 的原始 JSON 值区间做哈希。
首次成功取得非省略快照或指纹变化时才构建时间轴；缓存命中也仍校验歌词字段，
并非跳过解析或类型检查。指纹只取歌词值，不能用 `seq` 或整份响应，
否则位置更新就会触发时间轴重建并重置渲染状态。

## 版本兼容

- 字段只增不删；删除或改变语义必须递增 `v`，但当前 HTTP 客户端只接受 `v: 2`、`type: "snapshot"`。
- 未知版本、错误类型或缺失任一信封字段均拒绝，按一次失败处理，不会降级为整行显示；连续失败达到阈值后清空显示。
- 直接调用旧入口 `SnapshotParser.parseSnapshot` 时，仅在 `v` 与 `type` **同时缺失**时兼容无信封输入，其余必需字段仍须有效；只提供其中一个仍会失败。该入口捕获解析异常后返回空快照，不代表 HTTP 接受旧格式。
- HTTP 的 `sourceId` 由客户端数据源构造参数提供，不是响应必需字段。

## 尺寸与性能

- 单条 HTTP 响应体按字节有界读取，上限 4 MiB（`Protocol.MAX_PAYLOAD_CHARS`）；解析器另对字符串长度检查同一上限。
- 当前**没有**独立的「陈旧数据」判定。断连以连续失败 6 次为准，耗时包含每轮请求和轮间 200ms 等待，不保证 1.2 秒。
  曾有一个 `STALE_AFTER_MS` 常量承诺「超过 30 秒未响应则静默隐藏」，但对应机制从未实现，常量已删除——不要按那个行为设计适配器。

## 歌词源接口

**尚未实现。** 下面是设计的取数口径，不是现有代码。

计划中的内置歌词源将以 LRCLIB 为首个实现，例如：

- 精确查询：`GET /api/get?artist_name=&track_name=&album_name=&duration=`，`duration` 用于区分版本
- 模糊搜索：`GET /api/search?q=`
- 返回字段含 `syncedLyrics`（LRC 格式）与 `plainLyrics`，均无则为纯音乐

LRC 是行级格式，需要转成 `LyricTimeline`。逐字时间轴应优先取 TTML（AMLL 歌词库）而非 LRC。
